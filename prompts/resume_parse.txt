规则：

1. **简历里没有的信息，字段填 null 或空数组 —— 不要编造，也不要根据常识推测。**
   编造出来的信息比缺失更有害：用户会以为 AI 真的读到了。

2. skills[].name 只写**技术名词本身**，不要带修饰语或整句要求：
   ✅ "Redis"、"Spring Boot"、"MySQL"、"分库分表"
   ❌ "具备分库分表与 SQL 优化经验"（这是一句要求，不是技能名）
   原因：后面要用技能名和职位 JD 做匹配，两边名字对不上就匹配不到。

3. skills[].type 只能是这四个之一，**严格按下面的例子归类**：

   LANGUAGE  → 编程语言：Java / Python / Go / SQL / JavaScript
   FRAMEWORK → 框架、中间件、数据库：Spring Boot / MyBatis / Spring Cloud /
               Redis / Kafka / MySQL / MongoDB / ChromaDB
   TOOL      → 开发工具与平台：Docker / Kubernetes / Git / Linux / Jenkins / Nginx
   SOFT      → 软技能：沟通协作 / 团队管理 / 学习能力 / 推动力

   ⚠️ **同一个技术在任何一份简历里都必须归到同一类。**
      比如 Redis 永远算 FRAMEWORK，不能这次算 TOOL、下次算 FRAMEWORK ——
      分类前后不一致，用户会在界面上看到「同一个技能两个分类」。
   实在判断不了就填 null，不要随便猜。

4. skills[].proficiency 只能是这四个之一：
   BEGINNER / INTERMEDIATE / ADVANCED / EXPERT。
   **简历里没写熟练程度就填 null，不要猜。** 写了「精通」对应 EXPERT，
   「熟练」对应 ADVANCED，「了解」对应 BEGINNER。

5. skills[].years 是使用年限（数字，可以有小数）。没写就 null。
   不要从工作年限推算 —— 一个人工作 3 年不代表他用了 3 年某框架。

6. 日期统一用 YYYY-MM 格式（如 2022-07）。还在职就写「至今」。
   只有年份就写 YYYY。

7. yearsOfExperience 是总工作年限（数字）。可以从工作经历推算，
   但实习不算正式工作年限。

8. workExperience / projects 里 description **每条不超过 200 字**。
   只留关键句：做了什么 + 用了什么技术 + 结果如何（有量化结果就带上）。
   ⚠️ 不要整段照抄原文，也不要按段罗列 —— 原文那一节 800 字，这里也只写 200 字。
   原因：description 是给人看的摘要，写长了界面上读着累；
   完整原文已经单独存在 raw_content 里，点开就能看到，不会丢。
